# 🧠 Smart Light - BUMP Special Edition: 開發者設計精華日誌

這份文件記錄了本專案在開發過程中的核心技術決策、架構設計，以及如何解決硬體與網路同步中的「痛點」。這不僅是一份說明書，更是這個專案的技術精華總結。

---

## 🚀 1. 核心架構：異步雙軌監控 (Dual-Track Monitoring)

### 痛點
原本的系統是單執行緒（Single Thread）。主迴圈需要抓取股市 API (yfinance)，如果 API 延遲或卡住（常見現象），整個程式會停擺 5-30 秒。這會導致中央指令（如藍燈任務）反應遲鈍。

### 設計精華 (Gem)
我們在 `StockMonitor` 中引入了 **獨立任務監聽執行緒 (`_mission_worker`)**：
- **職責分離**：主執行緒負責「股市行情」監測，背景執行緒負責「中央指令」監聽。
- **秒級響應**：任務監聽緒每 1 秒輪詢一次伺服器。即使股市 API 卡死，燈光變藍的指令依然能在一秒內執行。
- **狀態鎖定**：一旦進入任務模式，主迴圈會自動進入 `sleep` 狀態，防止股市行情觸發的黃/紅/綠燈覆蓋掉 BUMP 的藍燈。

## 💡 2. 硬體控制優化：鎖定與防轟炸機制

### 痛點
1. **指令衝突**：每 2 秒一次的黃燈監控會與藍燈任務指令衝突，導致 Tapo 燈泡因為連線過多而「忙線拒絕」。
2. **語音重疊**：如果不加判斷，任務開啟後音響會每隔兩秒重複播放一次語音，造成吵雜、卡頓。

### 設計精華 (Gem)
- **變動觸發機制 (Change-Trigger-Only)**：
  - 系統會記錄 `_last_mission_msg`。只有當「任務狀態改變」或「任務文字改變」時，才會真正調用 Tapo API 和語音播報。
  - **好處**：極大降低硬體負荷，確保通訊穩定。
- **具備 Timeout 的非阻斷鎖 (`Lock with Timeout`)**：
  - 將關鍵指令（藍/紅/綠）的鎖改為 `acquire(blocking=True, timeout=1.0)`。
  - **原因**：如果只是 `blocking=False`，忙線時指令會直接丟失；如果無限制等待，會卡死程式。加上 `1.0s` 緩衝時間，確保關鍵指令有最高成功率下達到燈泡。

## 🌐 3. 中央伺服器設計：雲端持久化與 UX 優化

### 痛點
伺服器通常部署在 Render 等虛擬空間，重啟是常態。如果 BUMP 發布任務後伺服器自動重啟，任務狀態會歸零（變回一般模式）。

### 設計精華 (Gem)
- **JSON 持久化 (`server_state.json`)**：
  - 伺服器每次接收指令後都會寫入 JSON，啟動時優先讀取該檔案。
  - **效益**：即使伺服器自動睡眠/醒來，系統狀態依然保持一致。
- **BUMP 專屬 UX**：
  - 捨棄純 API 控制，改為**純網頁內置 (render_template_string)** 的 Dashboard。
  - 增加 `ADMIN_KEY` 認證介面，讓非技術人員 BUMP 只需要「輸入密碼 -> 點擊按鈕」即可操控。

## 🔒 4. 資安防禦：HTTPS 是鐵律 (Force HTTPS)

### 痛點
即便 BUMP 使用了複雜的密碼，如果連線是明文的 (HTTP)，駭客可以在同一個 Wi-Fi 下輕鬆攔截到密碼，進而奪取全台灣燈具的發言權。

### 設計精華 (Gem)
我們在 `central_command_server.py` 中實作了 **「多層強制加密」** 機制：
- **環境感知跳轉 (Auto-Redirect)**：
  - 伺服器會自動偵測 `X-Forwarded-Proto` 標頭（這是 Render 等雲端平台的標準）。
  - 如果偵測到使用者是用 `http://` 進入，程式會立即執行 **301 永久跳轉** 到 `https://`。
- **本地例外**：為了方便開發測試，如果是 `localhost` 或 `127.0.0.1`，跳轉機制會自動失效，避免本地開發難以調試。

## 🔊 5. 語音系統的多層防護 (Multi-Layer Voice)

### 痛點
`pyttsx3` 在某些版本的 Mac OS 或 Python 環境（如 3.12+）可能因為 `objc` 依賴問題初始化失敗。

### 設計精華 (Gem)
- **優雅降級 (Graceful Degradation)**：
  - 程式會嘗試初始化 `pyttsx3`，若失敗則在 `speak` 方法中自動 fallback 到 Mac 系統原生的 `subprocess.run(["say", text])`。
  - **效益**：確保在不同電腦環境下，BUMP 的語音簡報都能成功被「唸出來」。

## 📦 5. 技術名詞科普：什麼是 Payload (有效載荷)？

在開發過程中，你常會看到我們在傳送資料給伺服器時提到 `payload`。

### 核心概念
`Payload` 這個詞最早來自航空或物流。
- **飛機比喻**：一台飛機本身有機殼、引擎、燃油和機組人員，但這些都不是賺錢的東西。飛機真正載運的「貨物」或「乘客」，就是 **Payload (有效載荷)**。
- **網路傳輸**：在 HTTP 請求中，除了網址 (URL)、標頭 (Headers，如認證資訊) 這些必要的「包裝」外，你真正想要傳送給伺服器的**核心內容數據**，就是 Payload。

### 本專案實戰
當 BUMP 在控制台按下「發動任務」時，我們傳送的 Payload 如下：
```json
{
  "mode": "mission",
  "color": "blue",
  "message": "全體注意..."
}
```
伺服器並不在乎這封信是用什麼郵票（Headers），它只關心信件裡面的 **Payload**（任務資訊），因為那才是決定燈具如何運行的關鍵。

## 🛠 6. 總結：開發者的學習清單

如果你以後要開發類似的物聯網 (IoT) 監控系統，請記住這三個原則：
1. **不要相信網路 API 的延遲**：關鍵監控一定要開獨立 Thread。
2. **硬體是脆弱的**：不要高頻重複發送相同指令，用「狀態變動偵測」來執行硬體操作。
3. **UX 是核心**：給非工程師客戶的東西，一定要有網頁介面和簡單的登入機制。
