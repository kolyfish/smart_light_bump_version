# 🧠 Smart Light - BUMP Special Edition: 開發者設計精華日誌

這份文件記錄了本專案在開發過程中的核心技術決策、架構設計，以及如何解決硬體與網路同步中的「痛點」。這不僅是一份說明書，更是這個專案的技術精華總結。

---

## 🚀 1. 核心架構：異步雙軌監控 (Dual-Track Monitoring)

### 痛點
原本的系統是單執行緒（Single Thread）。主迴圈需要抓取股市 API (yfinance)，如果 API 延遲或卡住（常見現象），整個程式會停擺 5-30 秒。這會導致中央指令（如藍燈任務）反應遲鈍。

### 設計精華 (Gem)
我們在 `StockMonitor` 中引入了 **獨立任務監聽執行緒 (`_mission_worker`)**：
- **職責分離**：主執行緒負責「股市行情」監測，背景執行緒負責「中央指令」監聽。
- **秒級響應**：任務監聽緒每 1 秒輪詢一次伺服器。即使股市 API 卡死，燈光變藍的指令依然能在一秒內執行。
- **狀態鎖定**：一旦進入任務模式，主迴圈會自動進入 `sleep` 狀態，防止股市行情觸發的黃/紅/綠燈覆蓋掉 BUMP 的藍燈。

## 💡 2. 硬體控制優化：鎖定與防轟炸機制

### 痛點
1. **指令衝突**：每 2 秒一次的黃燈監控會與藍燈任務指令衝突，導致 Tapo 燈泡因為連線過多而「忙線拒絕」。
2. **語音重疊**：如果不加判斷，任務開啟後音響會每隔兩秒重複播放一次語音，造成吵雜、卡頓。

### 設計精華 (Gem)
- **變動觸發機制 (Change-Trigger-Only)**：
  - 系統會記錄 `_last_mission_msg`。只有當「任務狀態改變」或「任務文字改變」時，才會真正調用 Tapo API 和語音播報。
  - **好處**：極大降低硬體負荷，確保通訊穩定。
- **具備 Timeout 的非阻斷鎖 (`Lock with Timeout`)**：
  - 將關鍵指令（藍/紅/綠）的鎖改為 `acquire(blocking=True, timeout=1.0)`。
  - **原因**：如果只是 `blocking=False`，忙線時指令會直接丟失；如果無限制等待，會卡死程式。加上 `1.0s` 緩衝時間，確保關鍵指令有最高成功率下達到燈泡。

## 🌐 3. 中央伺服器設計：雲端持久化與 UX 優化

### 痛點
伺服器通常部署在 Render 等虛擬空間，重啟是常態。如果 BUMP 發布任務後伺服器自動重啟，任務狀態會歸零（變回一般模式）。

### 設計精華 (Gem)
- **JSON 持久化 (`server_state.json`)**：
  - 伺服器每次接收指令後都會寫入 JSON，啟動時優先讀取該檔案。
  - **效益**：即使伺服器自動睡眠/醒來，系統狀態依然保持一致。
- **BUMP 專屬 UX**：
  - 捨棄純 API 控制，改為**純網頁內置 (render_template_string)** 的 Dashboard。
  - 增加 `ADMIN_KEY` 認證介面，讓非技術人員 BUMP 只需要「輸入密碼 -> 點擊按鈕」即可操控。

## 🔒 4. 資安防禦：HTTPS 是鐵律 (Force HTTPS)

### 痛點
即便 BUMP 使用了複雜的密碼，如果連線是明文的 (HTTP)，駭客可以在同一個 Wi-Fi 下輕鬆攔截到密碼，進而奪取全台灣燈具的發言權。

### 設計精華 (Gem)
我們在 `central_command_server.py` 中實作了 **「多層強制加密」** 機制：
- **環境感知跳轉 (Auto-Redirect)**：
  - 伺服器會自動偵測 `X-Forwarded-Proto` 標頭（這是 Render 等雲端平台的標準）。
  - 如果偵測到使用者是用 `http://` 進入，程式會立即執行 **301 永久跳轉** 到 `https://`。
- **本地例外**：為了方便開發測試，如果是 `localhost` 或 `127.0.0.1`，跳轉機制會自動失效，避免本地開發難以調試。

## 🔊 5. 語音系統的多層防護 (Multi-Layer Voice)

### 痛點
`pyttsx3` 在某些版本的 Mac OS 或 Python 環境（如 3.12+）可能因為 `objc` 依賴問題初始化失敗。

### 設計精華 (Gem)
- **優雅降級 (Graceful Degradation)**：
  - 程式會嘗試初始化 `pyttsx3`，若失敗則在 `speak` 方法中自動 fallback 到 Mac 系統原生的 `subprocess.run(["say", text])`。
  - **效益**：確保在不同電腦環境下，BUMP 的語音簡報都能成功被「唸出來」。

## 📦 5. 技術名詞科普：什麼是 Payload (有效載荷)？

在開發過程中，你常會看到我們在傳送資料給伺服器時提到 `payload`。

### 核心概念
`Payload` 這個詞最早來自航空或物流。
- **飛機比喻**：一台飛機本身有機殼、引擎、燃油和機組人員，但這些都不是賺錢的東西。飛機真正載運的「貨物」或「乘客」，就是 **Payload (有效載荷)**。
- **網路傳輸**：在 HTTP 請求中，除了網址 (URL)、標頭 (Headers，如認證資訊) 這些必要的「包裝」外，你真正想要傳送給伺服器的**核心內容數據**，就是 Payload。

### 本專案實戰
當 BUMP 在控制台按下「發動任務」時，我們傳送的 Payload 如下：
```json
{
  "mode": "mission",
  "color": "blue",
  "message": "全體注意..."
}
```
伺服器並不在乎這封信是用什麼郵票（Headers），它只關心信件裡面的 **Payload**（任務資訊），因為那才是決定燈具如何運行的關鍵。

## 🛠 10. V1.2 工程化優化：維護與異地部署 (Maintenance & Remote Deployment)

### 痛點
隨著系統開始在不同電腦上部署，維護成本（如金鑰外洩、Tapo IP 變動、系統環境差異）會呈指數成長。如果開發者必須親自到每一台電腦前 debug，系統就無法規模化。

### 設計精華 (Gem)
- **環境自癒與分離 (Self-Healing Environment)**：
  - **腳本化安裝**：開發了 `install_and_run` 系列腳本，自動建立 `venv` 並隔離依賴。這解決了「在我電腦可以跑，你那邊不行」的經典 Python 環境問題。
  - **配置外置化**：所有的燈泡設定都存在 `config.json`，而 API URL 則優先由環境變數決定。這讓同一套代碼可以在「測試」與「生產」環境無縫切換。
- **維護文件化 (Living Documentation)**：
  - 引進 `maintenance_guide` 與 `remoting_setup`。這不是為了湊字數，而是為了將技術決策「降維代償」成操作步驟，讓非核心開發者甚至是資深使用者（Power User）也能參與維護。
- **控制與監聽解法 (Decoupled Logic)**：
  - 將「發布任務」與「網頁控制台」邏輯分離。開發者可以使用 `trigger_mission.py` 在終端機快速測試，而 BUMP 使用網頁版。這種多入口設計（Multi-Entry）極大提升了調試效率。

  - **UX 優化**：輸入框會根據伺服器當前狀態「自動填入」，減少重複輸入的疲勞感，同時確保指令下達的一致性。

## 🔒 12. V1.4 強化：生產環境安全性加固 (Security Hardening)

### 痛點
即便有了環境變數，若程式碼中仍遺留預設的「開發用金鑰字串」(Default Secrets)，則在生產環境中依然存在被破解的風險。此外，分散的金鑰管理邏輯會導致配置不一致。

### 設計精華 (Gem)
- **環境驅動簽名 (Environment-Driven Signing)**：
  - **設計**：將產品序號 (License Key) 的校驗 Salt 統一指向 `.env` 中的 `SECRET_KEY`。
  - **影響**：這使得金鑰具備了「唯一性」與「環境隔離性」。同一個序號在開發機與生產機（若金鑰不同）將無法通用。
- **無硬編碼原則 (No Hard-coded Secrets)**：
  - **實作**：全面移除 `license_manager.py` 與 `license_generator.py` 中的字串實體。
  - **價值**：真正實現了「程式碼與配置分離」，符合生產環境安全性規範（Twelve-Factor App）。

## 🏗 13. V1.5 重構：專業化目錄結構與門面模式 (Facade Pattern)

### 痛點
隨著功能的增加，根目錄堆滿了 `.py`, `.json`, `.txt`, `.md` 與 `.log` 檔案。對於開發者來說難以管理，對於「傻瓜」使用者來說更是找不到啟動點。

### 設計精華 (Gem)
- **職責分離 (Separation of Concerns)**：
  - **`src/`**：核心代碼，與外部配置完全解耦。
  - **`config/`**：持久化狀態與敏感數據的避風港。
  - **`scripts/`**：將「開發工具」與「使用者指令」獨立，避免混淆。
- **門面模式 (Facade Pattern) 入口**：
  - **設計**：引入根目錄的 `main.py`。
  - **實現**：透過自定義的 `sys.path` 注入，讓使用者只需執行 `python main.py`，其餘複雜的模組依賴載入與路徑管理都在後台自動完成。
  - **價值**：極簡的使用者介面。不管內部的 `src` 怎麼變動，使用者的啟動方式永遠不變。

## 🛠 14. V1.6 進化：本地/生產連線隔離與語音穩健性 (Connection Isolation & Voice Robustness)
 
### 痛點
1. **指令污染**：當開發者在本地測試時，客戶端若預設連向雲端 Render，會接收到與預期不符的生產指令（如 `EXECUTE_ORDER_66`）。
2. **語音沉默**：`pyttsx3` 在某些 Mac 系統版本上雖回傳成功，但實際上並未發聲，這對於警報系統是致命的。
 
### 設計精華 (Gem)
- **連線路徑解耦 (URL Decoupling)**：
  - **實作**：將 `MISSION_CONTROL_URL` 完全外置於 `.env`。
  - **價值**：開發測試時可指向 `localhost:5010`，生產環境則指向 Render。確保「情報網」與「指揮部」精準對接。
- **強制原生語音 (Forced Native Say)**：
  - **設計**：引入 `FORCE_NATIVE_SAY` 開關。
  - **實現**：既然是為 Mac 打造的系統，直接將 Mac 內建的 `say` 指令提升為一等公民（First-class citizen），而非僅作為降級方案。
  - **價值**：徹底解決第三方套件在 macOS 上的不穩定性，確保 BUMP 的每一句指令都能響徹雲霄。
